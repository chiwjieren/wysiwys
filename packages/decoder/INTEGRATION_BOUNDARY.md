# Decoder consumer boundary

Build with `npm run build --workspace=packages/decoder`, then import `decodeVaultTransaction` and the `DecodeResult` and `DecodedAction` types from `@wysiwys/decoder`. The package root resolves to the generated JavaScript and declaration files. These decoder-facing types remain provisional in this package pending team review; Guard contracts live in `packages/shared`.

The caller computes `txHash(vaultTransactionAddress, fullAccountData)` from `@wysiwys/shared` and compares it with the Guard Review before invoking the decoder. The hash uses the `wysiwys:tx:v1` domain, the 32-byte account address and the full account data. A mismatch stops before decoding. The caller passes `result.actions` to policy only when `result.status === 'success'`; `unsupported` and `malformed` results carry no actions. The decoder does not verify hashes or make policy decisions.

`test/boundary.test.ts` exercises the call order with an upstream hash mock and the real shared `txHash` function, the package import, real and synthetic account fixtures, and a downstream policy mock. `test/browser-import.ts` is typechecked with DOM types and no Node types, and bundles for the browser. The source and browser bundle have no Node runtime, filesystem, network, clock, or randomness dependency.

`test/cre-smoke/main.ts` imports the package under a CRE-style TypeScript configuration with no Node types. Run `npm run typecheck:cre --workspace=packages/decoder` after building the decoder. On 6 October 2026, this probe was copied into an isolated project with the built local decoder, Bun `1.2.21`, and the official `@chainlink/cre-sdk` compiler `1.22.0`. Running `bun node_modules/@chainlink/cre-sdk/bin/cre-compile.ts workflow.ts decoder-package-smoke.wasm` there bundled the decoder and produced a WASM binary. The isolated project supplies the SDK dependency that the compiler injects into its entry point. This is a package compatibility check, not execution of the Wysiwys workflow.

The repository currently has no CRE workflow source or target configuration, so an import and build against the actual project workflow remains an integration gate. The CRE CLI's project initialization requires authentication. The package and isolated smoke builds do not prove the full workflow integration.
